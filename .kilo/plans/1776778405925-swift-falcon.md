# Plan: Stabilisation Supabase (Barrel + FriendService)

## Résumé
Corriger l'erreur de build dans le barrel `src/lib/supabase/index.ts`, maintenir une API d'import propre, et renforcer le typage de `FriendService` pour aligner avec le schéma `Database`. Le client Supabase utilisé est basé sur la bibliothèque officielle `@supabase/supabase-js`, offrant compatibilité complète, sécurité et fonctionnalités maintenues par Supabase.

## Contexte et Justification
### Pourquoi utiliser le client Supabase officiel ?
Le projet utilise déjà le client officiel de Supabase JS (`@supabase/supabase-js`) dans tous les wrappers personnalisés :
- `getSupabaseClient()` (client-side) : Utilise `createBrowserClient<Database>()` pour une instance typée et sécurisée pour le navigateur.
- `getUserSupabaseClient(auth)` (server-side) : Utilise `createClient()` avec authentification utilisateur pour les routes API.
- Ces wrappers sont nécessaires pour la gestion d'authentification et la sécurité (RLS), mais reposent sur le client officiel pour toutes les fonctionnalités.

Avantages du client officiel vs un client personnalisé :
- **Type safety complète** : Avec `SupabaseClient<Database>`, on obtient autocomplétion et validation des requêtes SQL contre le schéma réel.
- **Sécurité et performance** : Implémentation optimisée, mises à jour régulières, et support officiel pour RLS, auth, realtime, etc.
- **Maintenance** : Pas besoin de réimplémenter des fonctionnalités complexes comme la gestion d'auth ou les requêtes avancées.
- **Compatibilité** : Garantie de compatibilité avec les services Supabase (database, auth, storage).

Le client "personnalisé" du projet est en fait un wrapper léger autour du client officiel, adapté aux besoins d'authentification côté serveur. Nous le conservons car il est essentiel pour les routes API, mais nous renforçons son typage.

## Changements d'Implémentation
### Mise à jour de `src/lib/supabase/index.ts`
- Supprimer l'export invalide `supabaseClient` (non exporté par `client.ts`, causant l'erreur de build).
- Garder uniquement `export { getSupabaseClient } from './client';`
- Mettre à jour les commentaires d'exemple pour refléter l'usage correct : importer `getSupabaseClient` au lieu de `supabaseClient`.

### Renforcement du typage dans `src/lib/domain/services/FriendService.ts`
- Importer `Database` depuis `database.types`.
- Changer `private supabase: SupabaseClient;` en `private supabase: SupabaseClient<Database>;`
- Garder la source du client inchangée (`getUserSupabaseClient(auth)`), seulement améliorer le typage pour bénéficier de la validation des requêtes.

### Vérification des exports Supabase
- Confirmer que le barrel n'expose que des symboles exportés : `getSupabaseClient`, `getSupabaseAdmin`, `supabaseServerPool`, `Database`.
- Éviter de réintroduire un client global non typé pour maintenir la séparation auth/session.

## API / Interfaces Impactées
- **@/lib/supabase** : Suppression de l'export non fonctionnel `supabaseClient`. Les autres exports restent inchangés.
- **FriendService** : Typage interne renforcé sans changement du contrat public de la classe (constructeur et méthodes publiques identiques).
